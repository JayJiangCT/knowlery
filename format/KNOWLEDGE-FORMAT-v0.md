# Knowlery Knowledge Format v0 — Working Draft

> **STATUS: DRAFT / NON-NORMATIVE**  
> 目标是统一研究问题、最小语义边界和待评测方案。**这不是已批准的 Schema，也不要求现有 Vault 迁移。**

## 1. 为什么需要 Format

Knowlery 2.0 以开放 Markdown Wiki 为长期资产。格式要保证不同 Agent、Obsidian、无 Obsidian 工具都能理解当前知识、证据、关系、变化和治理状态，而不要求所有工具采用相同检索索引或排序。

这里的“格式”不只是 YAML 字段：还包括 **Wiki 信息组织方式 + 语义 + 必需的安全操作契约**。

## 2. 先定义使用场景，再决定字段

同一个 Agent 接到“为什么不再自研 Core Runtime？”时，应该能按需得到：
- 当前采用的结论，以及适用范围；
- 为什么采纳该结论、放弃哪些备选；
- 直接来源、来源版本、支持与反对证据；
- 已知例外、未决事项及重要历史；
- 同主题知识的关系与最近一次实质变化。

Agent 不能为了得到“当前结论”而被迫从长篇历史记录中猜测，也不能把过去的研究快照当成最新权威。

## 3. 初步组织假设：Structured Topic Wiki

**候选，而非已批准**。优先保留 1.x 成熟的主题 Wiki 及 Entities、Concepts 等已有内容，不强制把 194 篇已编译文件变成大量原子事实。

考虑一篇主题页提供：

1. **Current Knowledge**：最常用、当前有效的核心结论、条件及未决事项；
2. **Explanation / Mechanism**：理解与使用这些结论所需的机制和上下文；
3. **Relations & Evidence**：来源、相关知识、支持/反对关系；
4. **History on demand**：被取代的决定、研究快照和修订历史，按需展开。

这些是信息组织的工作假设，**不是四个必须具有相同标题的 Markdown Section**。不预先确定文件数量、大小门槛、知识目录或拆分策略。

## 4. 语义需求（候选最低保证）

| 维度 | 期望保证 | 尚未决策的实现 |
| --- | --- | --- |
| 内容可移植 | 正文为可阅读的 Markdown，不依赖唯一客户端解释基本含义 | 标准 Markdown 链接与 Wikilink 的兼容级别 |
| 当前性 | Agent 能区分当前结论、历史快照、失效/取代内容 | 状态字段、有效时间与优先级 |
| 来源 | 关键结论能指出实际依据的材料和位置 | 引用粒度、片段定位、外部链接表示 |
| 版本 | 能解释编译/修订时读过哪个来源版本，无法证明时明确标记 | 快照、Git 历史、片段和 hash 的组合 |
| 关系 | 描述相关、依赖、支持、冲突和取代关系，并可检查有效性 | 关系表示、循环与失联处理 |
| 治理 | 重要采纳、拒绝、废弃、取代决定可在不同设备恢复 | sidecar / 文档内结构 / 独立记录 |
| 更新安全 | 不静默覆盖人工或其他 Agent 修改；保留重要历史 | 版本锁、局部 patch、冲突合并和恢复 |
| 可扩展 | 不认识 Knowlery 的工具仍可打开文件；认识扩展的工具能解释元信息 | 命名空间、版本号、扩展兼容性 |

注意：**人工批准不是事实真理证明；来源记录不是事实本身永远正确的证明。**

## 5. 资产逻辑分类

以下是职责分析，而非五套强制存储：

- **原始资料**：人或 Agent 输入的笔记、文档、附件及外部链接；不可假设内容可随时重建。
- **来源版本与证据记录**：说明某次结论依据的确切资料、片段与版本；仅 hash 不能恢复历史原文。
- **加工 Wiki**：知识及其人工修订，可能成为用户长期资产，不能全部视为可丢弃缓存。
- **治理记录**：重要批准/拒绝/废弃/取代及原因，不能只存在一次性的 Agent 会话。
- **运行索引与执行状态**：索引可重建，不能代替前面四类持久资产。

## 6. 非规范性示例（仅用于讨论）

下面的 Frontmatter **不构成最终字段规范**，`type`、`status`、`sources` 不代表已批准的必填字段。例子刻意保持简单：

~~~yaml
---
type: concept
status: reviewed
sources:
  - Projects/Database-Decision.md
---

# Database Strategy

## Current Knowledge

当前结论与适用条件（示意）。

## Evidence & History

来源定位及过去被替代的选项（示意）。
~~~

仅凭 `sources` 路径，不能证明它引用了源文件的哪一个历史版本。若同路径文件被替换、源文件改名或多人并发编辑，仍需补充可靠的身份、版本和冲突机制。

## 7. 关键反例

- Wiki 顶部标记 `status: active`，但内容还指向新的 `superseded_by`：Agent 不能仅看 `active` 就判为当前有效。保存状态、事实当前性和取代关系需要区分。
- 同一结论同时引用原始笔记 A 和对 A 的另一篇汇总 Wiki B：这不是两份独立直接证据。
- 两个客户端可阅读同一组 Markdown，但一个只能全文匹配，另一个有 Obsidian Link Cache：不要求搜索排名相同，但都不得误用失效决定。
- 用户编辑了编译页后，后台编译发布旧基线：必须阻止静默覆盖。
- 来源丢失或历史版本不可恢复：应声明证据缺口，不得伪造引文。

## 8. 首批决策与实验

1. 用 Parallel Search 知识簇比较 1.x、结构优化 Topic Wiki 和支持局部更新的 Topic Wiki。
2. 优先确定 Current Knowledge、演进和关系在 Agent 使用中的信息需求，再讨论字段 Schema。
3. 决定兼容旧 Raw Markdown 的最低要求，以及是否对**部分受管理对象**引入稳定 ID；不要批量注入 UUID。
4. 对来源片段、时间、身份、引用类型与治理状态建立可检验的保证等级。
5. 定义不依赖 LLM 自觉遵守的写入安全和测试协议。

测试细节：[VALIDATION.md](../docs/2.0/VALIDATION.md)。状态与 Owner 待决：[DECISIONS.md](../docs/2.0/DECISIONS.md)。

## 9. 本草案不能被当作

- 已发布 `knowlery-format@1`、固定 Frontmatter Schema 或兼容性认证；
- 建议立即迁移所有 1.x Wiki 或重写用户原始笔记；
- 对所有 Agent 的检索准确率、Token 节省或自治质量的已测保证。
