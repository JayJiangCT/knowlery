# Knowlery 2.0 — Validation Plan

> 状态：待执行测试计划；以下不是当前产品已达到的性能或功能证明。

## 共用样本

以现有 Knowlery-Pilot 的编译 Wiki 和 G0/G1 问题集作为起点。既有审查快照包含 194 篇编译 Wiki（Entities 14 / Concepts 46 / Queries 131 / Comparisons 3）；这些数字是特定快照，不是此分支重新测量的最新结果。

优先选取 **Parallel Search** 知识簇，包含当前规则、历史方案、多轮修订、相关实体、研究及决策。更新类测试仅使用 Pilot 的独立可写副本；Pilot 原本只读。

## 三组对照

1. 原有 1.x Topic Wiki。
2. 当前知识与历史上下文重新组织的 Topic Wiki。
3. 在 2 基础上支持局部定位和局部更新的 Topic Wiki。

相同问题、相同评测条件、保留模型与 Harness 版本。以准确性、引用与当前性为质量护栏，再比较上下文/Token 成本。

## 必要的行为测试

| 场景 | 必须验证的结果 |
| --- | --- |
| 关闭 / 卸载 Obsidian | Agent 仍可理解 Wiki、检索来源并开展受支持的工作流 |
| 已失效的历史决策 | Agent 不把被取代结论误报为当前有效 |
| 新来源影响局部规则 | 只变更相关知识，并保留必要历史 |
| 两份同等权威资料相互矛盾 | 保留冲突，不无依据地选择获胜者 |
| 外部编辑与 Agent 发布并发 | 不静默覆盖，能保留未解决的差异 |
| 来源已修改或丢失 | 如无法证明当时依据，明确指出追溯限制 |
| 索引损坏或更换检索后端 | 不丢失知识、证据或治理决定 |
| 不同 Harness / Adapter | 关键含义、状态与写入安全一致；不要求搜索排名完全一致 |

## 度量

回答正确率、当前有效结论识别、证据定位正确性、局部更新精度、冲突处理与数据保全、Token 消耗、人工介入率、平台移植能力。定义评分规则与基线后再设门槛，不预先编造提升比例。

## 实施要求

- 每个实验保存固定输入、版本、预期结果、实际输出与差异。
- 标出简化假设；不可把工具行为“看起来相近”当作通过语义符合性。
- 验收失败时优先修订 Format / Skills / 操作契约，再考虑扩展 Runtime。
- 将未来的测试用例放在 [tests/conformance/](../../tests/conformance/)；本次仅建立入口。
